## 1. PURPOSE

Web-based video player for ONE full-length story-driven piece
(TV episode or 20-30 min film) that shows personalized
NON-SPEECH captions (e.g. "[soft piano music]") for Deaf and
hard-of-hearing (DHH) viewers, and is evaluated with DHH
participants against a fixed-caption baseline.

Research question: How can personalized non-speech captions adapt
across long-form, story-driven video while staying consistent,
understandable, and under the viewer's control?

Scope: non-speech sound captions only. NOT general subtitling,
NOT live captioning, NOT speech-prosody styling.

Team: Zuhair Amirali Merchant (29021), Muhammad Hamza Kashif
(29022), Immaduddin Durrani (29204).

## 1a. HCI / ACCESSIBILITY DESIGN PRINCIPLES

- Viewer control comes first. A one-tap "Show Original" (the
  creator's caption) is always reachable. Some participants in
  prior work disliked customization entirely.
- No hidden adaptation. If a caption changed because of the scene,
  the viewer can find out why (on-demand disclosure, e.g. hover or
  tap). [PROPOSED, experimental]
- Simple controls over dense ones. Prior work criticized a 10x10
  detail/expressiveness grid; use a coarse scale (3-5 levels) or
  presets. [PROPOSED, experimental]
- Progressive disclosure: few controls first, advanced later.
- Caption text: readable contrast, resizable, never covering
  critical on-screen content; full keyboard operation of the
  player and controls; check against WCAG guidance. [PROPOSED]
- Desktop/laptop/tablet are the study targets. Phone layout should
  work but is not the design driver. [PROPOSED]
- Don't overclaim in the writeup: prior studies are small
  qualitative samples (see section 13).

## 3. CORE PRINCIPLE: PRECOMPUTE, NEVER CALL NIM DURING VIEWING

- No NIM call happens while a participant watches. Every caption
  variant a viewer can select is generated once, offline, and
  stored as JSON. The viewer only picks a cached variant.
- Effect: the 40 RPM cap limits only how fast we can INGEST a new
  video, not how many people watch or how long a session runs.
- Scene-context extraction is cached separately from caption
  variant generation, so changing the caption prompt does not
  force re-running the expensive context step.

## 4. INGESTION PIPELINE (LOCAL, ONE VIDEO AT A TIME) [PROPOSED]

1. Input: video file + any existing caption/subtitle file.
2. Cue list: (a) detect bracketed/parenthetical non-speech cues in
   SDH-style subtitles if they exist; (b) otherwise generate cues
   from the audio with a NIM model. Do NOT assume a source's
   subtitles contain non-speech cues.
3. Context window: extract a few seconds of audio+video around
   each cue (ffmpeg, local).
4. Scene context call: NIM omni model produces a scene/sound
   description per cue. Candidate: nemotron-3-nano-omni-30b-a3b-
   reasoning. Fallback (video/image only, no audio): cosmos3-nano-reasoner.
   If the omni model cannot label non-speech sounds reliably,
   audio cues need another source (SDH captions, or a local
   audio-event tagger, not yet researched).
5. Caption variants call: one structured-JSON call per cue
   returns the whole grid (candidate 3x3: Level of Detail x
   Expressiveness) plus 2-3 sound-representation variants. Pass a
   running glossary of already-captioned sounds so the same sound
   gets consistent wording across the video.
   Candidate model: nemotron-3.5-lightning-30b-a3b, fallback
   gpt-oss-20b. Larger models only for an optional quality pass.
   [UNVERIFIED, see 0a]
6. Validate every response against the schema (retry once on bad
   JSON), write one JSON per video. Human review pass over the
   output before it goes into a study (consistency, hallucinated
   sounds, tone).
7. Call-count estimate: roughly 2 calls per cue. With 100-300
   cues per film, ~200-600 calls, i.e. about 5-20 min at 30 RPM.
   These cue counts are a GUESS; measure on the first video.
- NIM API key lives in a local .env only. Never committed, never
  in a NEXT_PUBLIC_* variable, never on the host.

## 5. PRECOMPUTED DATA SCHEMA [PROPOSED, not built]

One JSON file per video, e.g. data/captions/{video_id}.json:
  video_id, title, source_url, license, duration_seconds,
  schema_version, generated_with (model names, prompt version)
  cues: [
    { cue_id, start_s, end_s, original_text,
      scene_context (short text),
      sound_key (normalized label used for consistency),
      grid: { "<detail>-<expr>": text, ... },
      representations: { descriptive, onomatopoeic?, plain } }
  ]
Viewer state is a small profile object stored in the browser
(and logged for the study), not in this file.

## 6. RUNTIME BEHAVIOR (HOSTED APP)

- Loads the video's JSON and the viewer's profile.
- Persistent caption profile: detail/expressiveness set once,
  applied for the whole runtime. [DECIDED in proposal]
- Scene-aware adaptation: shorter/simpler captions during dense or
  fast scenes, richer during quiet or off-screen sound. HOW a scene
  is classified is NOT decided. [PROPOSED] derive it from
  ingestion-time metadata (e.g. cue density per time window) so
  no live computation is needed.
- "Show Original" toggle: swaps to the creator's stored caption.
  [DECIDED in proposal]
- Preview pane: renders sample cues from the cached grid under a
  candidate setting before committing. [DECIDED in proposal]
- Baseline condition for the study: fixed original captions.
- All of the above are cache lookups; no model calls.

## 13. RESEARCH GROUNDING (what the papers do and don't support)

Counts below were taken from earlier chat notes, not re-read from
the papers. [UNVERIFIED] Re-check each figure in the source
before citing it.

CapTune (Huang et al., ASSETS '25, arXiv:2508.19971): the closest
prior work. Small qualitative samples (12 DHH viewers, 7
creators). Its evaluation used 2-8 minute clips. Reported themes
that motivate this project: wanting persistent profiles across
videos, preview before committing, dense grid controls hard to
use, fast/dense captions hard to follow, richer captions wanted
for off-screen sound, discomfort when captions feel too
interpretive, and the same sound sometimes captioned differently
within a video.

CuCap (de Lacerda Pataca et al., ASSETS '25): about speech
prosody/emotion styling, NOT non-speech captions. Use only its
design philosophy (progressive disclosure, defaults with override,
genre presets). Do not cite its numbers as evidence about
non-speech sound.

Interpretive Caption (Ubur et al., ASSETS '25): real-time speech
emotion cues for live lectures, 8 participants, exploratory. Use
only the on-demand disclosure UI idea. It does not validate
anything about non-speech captions or long-form video.

Open questions this project tests (no prior evidence):
- Does a persistent profile stay consistent over 20-90 minutes?
- Does reading fatigue compound over a full runtime?
- Does same-sound inconsistency worsen at length; does a
  glossary/lock per sound_key fix it?
- Do viewers want scene-level overrides on top of a global
  profile?
- Does a coarse 3-5 level scale beat a fine slider?
- Do genre-based presets reduce onboarding friction?
